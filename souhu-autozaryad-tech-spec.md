# Автозаряд энергии TRON через API Souhu — техническое ТЗ

## 1. Цель

Добавить в существующий Telegram-бот аренды TRON Energy услугу **«Автозаряд»**. Клиент один раз подключает свой TRON-адрес и пополняет баланс. Далее Souhu самостоятельно поддерживает на адресе делегированную энергию, а наш сервис:

- принимает оплату и ведёт розничный баланс клиента;
- включает, приостанавливает и пополняет автозаряд у Souhu;
- регулярно получает историю фактического расхода;
- списывает с клиента розничную цену каждой выдачи энергии;
- показывает историю, остаток, прогресс по тарифу и предупреждения.

Клиент не передаёт приватный ключ или seed-фразу. Нужен только публичный TRON-адрес.

## 2. Важная модель услуги

Автозаряд — **не подписка и не пакет энергии**, а предоплаченный режим обслуживания адреса.

Есть три разных денежных сущности:

| Сущность | Где учитывается | Назначение |
|---|---|---|
| Розничный баланс клиента | В нашей БД | Деньги клиента по нашим ценам |
| Рабочий кредит адреса | У Souhu | Из него Souhu списывает свою закупочную цену за выдачи энергии |
| Залог | У Souhu | Условие льготного тарифа Pro / Max / Ultra |

Нельзя считать эти остатки одним балансом. В интерфейсе клиента показывать только его розничный баланс и отдельно статус залога. Рабочий кредит Souhu — внутренний технический показатель.

## 3. Тарифы и соответствующие значения API

Расчётный период — **72 часа**, не 48.

| Тариф в боте | Значение `channel` в Souhu | Минимум расхода за 72 часа | Залог |
|---|---|---:|---:|
| Обычный автозаряд | `normal` | нет | нет |
| Автозаряд Pro | `high_frequency` | 460 000 энергии | 15 TRX |
| Автозаряд Max | `jisu_frequency` | 1 310 000 энергии | 15 TRX |
| Автозаряд Ultra | `guangsu_frequency` | 3 910 000 энергии | 15 TRX |

По публичным объявлениям Souhu тарифы с минимумом рассчитаны на активных клиентов. Залог должен автоматически возвращаться при выполнении условия периода. Поведение при невыполнении минимума и запуске следующего периода требуется подтвердить тестом с реальным API — см. раздел 12.

## 4. API Souhu

Base URL:

```text
https://weidubot.cc/api/v2
```

### 4.1 Подпись каждого запроса

В заголовках обязательны:

```text
x-api-key: <API_KEY>
x-timestamp: <Unix timestamp в секундах>
x-signature: <lowercase hex>
```

Подпись:

```text
HMAC-SHA256(key = API_SECRET, message = API_KEY + timestamp)
```

Время должно отличаться от серверного не более чем на ±5 минут. API key и secret хранятся только в серверных переменных окружения / credential storage n8n. Ни в Mini App, ни в клиентском браузере, ни в Telegram-сообщениях этих ключей быть не должно.

### 4.2 Используемые методы

| Метод | Зачем нужен |
|---|---|
| `GET /get_smart_price` | Получать актуальные закупочные цены умного автозаряда |
| `POST /delegate_energy_smart` | Первичное подключение и добавление рабочего кредита |
| `GET /query_energy_smart?address=...&page=...` | Статус, остаток и постраничная история фактических расходов |
| `POST /update_energy_smart` | Пауза и повторный запуск сервиса |
| `GET /statistics_smart_by_address?address=...` | Агрегированная статистика по 65K и 131K |
| `GET /user_info` | Проверка состояния аккаунта Souhu / операторского остатка, если метод отдаёт его |

В Swagger отсутствует webhook / callback. Поэтому синхронизация выполняется только polling-ом API.

## 5. Подключение автозаряда

### 5.1 Клиентский сценарий

1. Клиент выбирает адрес и тариф.
2. Бот показывает условия, минимум за 72 часа, залог и актуальную цену 65K/131K.
3. Клиент пополняет:
   - залог 15 TRX для Pro / Max / Ultra;
   - рабочий розничный баланс для будущих выдач энергии.
4. После подтверждения платежа сервер создаёт запись автозаряда и вызывает Souhu.
5. Клиент видит статус «Подключён» только после успешного ответа Souhu.

### 5.2 Первый вызов Souhu

`POST /delegate_energy_smart`, тип тела `application/x-www-form-urlencoded`.

Пример для Pro:

```text
address=T...
balance=<рабочий_кредит_для_Souhu>
channel=high_frequency
hf_deposit=15
net_protect=<серверная настройка>
```

Для Max и Ultra менять только `channel`:

```text
Max   → jisu_frequency
Ultra → guangsu_frequency
```

Параметр `balance` — положительное число в TRX, которым увеличивается кредит данного адреса в Souhu. Он не равен автоматически розничному балансу клиента в нашей БД.

`hf_deposit`:

| Значение | Значение в документации Souhu |
|---:|---|
| `-1` | использовать системный залог Souhu |
| `0` | не удерживать залог |
| `15` | удержать конкретный залог 15 TRX |

При первичном запуске Pro / Max / Ultra передавать `hf_deposit=15`. При обычном повторном пополнении рабочего кредита `hf_deposit` не передавать, пока Souhu не подтвердит правила повторного удержания.

`net_protect` поддерживает `open` / `close`, но Swagger не описывает фактическое поведение. Не выводить этот переключатель клиенту. Сделать серверной конфигурацией и выбрать значение только после теста.

## 6. Деньги и наценка

### 6.1 Рекомендуемая модель цены

Использовать тот же принцип, что в текущей аренде 65K/131K: закупочная цена плюс отдельная фиксированная наценка.

```text
розничная цена 65K  = закупочная цена Souhu 65K  + delta_autocharging_<tariff>_65k
розничная цена 131K = закупочная цена Souhu 131K + delta_autocharging_<tariff>_131k
```

Настройки должны быть независимыми для `pro`, `max`, `ultra` и редактироваться администратором без деплоя.

Пример только для понимания модели:

```text
Souhu Pro 65K:          1.70 TRX
Наша наценка:           0.30 TRX
Клиентская цена 65K:    2.00 TRX

Souhu Pro 131K:         3.40 TRX
Клиентская цена 131K:   4.00 TRX
```

После одной выдачи 65K:

```text
закупочный расход:  1.70 TRX
списание с клиента: 2.00 TRX
валовая маржа:      0.30 TRX
```

Не зашивать цены в код. Запрашивать их при открытии экрана тарифа и периодически синхронизировать. Формат ответа актуального `/get_smart_price` для новых каналов `jisu_frequency` и `guangsu_frequency` необходимо проверить на живом API: старая версия Swagger явно описывает только normal / high frequency.

### 6.2 Что взять с клиента при первом подключении

Клиент платит:

```text
залог + начальный розничный рабочий баланс
```

Минимальную рекомендуемую сумму считать динамически:

```text
минимум_пополнения =
  залог
  + (минимум_энергии_тарифа / 65000) × клиентская_цена_65K
  + запас 10–15%
```

При розничной цене 2.00 TRX / 65K ориентировочно:

| Тариф | Минимум на энергию | Залог | Практичный первый платёж |
|---|---:|---:|---:|
| Pro | ~14.2 TRX | 15 TRX | 30–35 TRX |
| Max | ~40.4 TRX | 15 TRX | 60–65 TRX |
| Ultra | ~120.4 TRX | 15 TRX | 140–150 TRX |

Это не фиксированные тарифы. Значения меняются с закупочной и розничной ценой.

### 6.3 Рабочий кредит Souhu

Souhu списывает свою закупочную цену с кредита адреса. У нашего сервиса должен быть операторский резерв, потому что не стоит рассчитывать на мгновенную синхронизацию с клиентским балансом.

Рекомендуемая логика:

1. У клиента есть `retail_balance_trx` в нашей БД.
2. После обнаружения фактического расхода списываем с него нашу цену.
3. Поддерживаем у адреса небольшой технический кредит Souhu — например, на 2–3 ожидаемые выдачи.
4. Если клиентский баланс меньше цены следующей выдачи с запасом, отправляем `status=stop`.
5. При пополнении клиента снова добавляем кредит Souhu и запускаем `status=start`.

Возможен риск одной лишней выдачи до очередного polling-а. Он должен быть учтён в операционном резерве и марже.

## 7. Как узнавать о расходе и не списывать дважды

Souhu сам отслеживает использование делегированной энергии. Наш сервис ничего не подписывает в кошельке клиента и не должен самостоятельно угадывать его USDT-переводы.

CRON каждые **60–180 секунд** для активных автозарядов:

```text
GET /query_energy_smart?address=<TRON_ADDRESS>&page=<N>
```

В истории ожидаются поля:

| Поле | Использование |
|---|---|
| `used_tx_id` | Хеш транзакции клиента; основной ключ для идемпотентности |
| `used_energy` | Фактический расход энергии |
| `energy_type` | `65k` или `131k` |
| `amount` | Фактическая закупочная сумма Souhu |
| `balance` | Остаток кредитов данного адреса у Souhu |
| `delegate_tx_id` | Транзакция делегирования энергии |
| `un_delegate_tx_id` | Транзакция отзыва делегации |
| `status` | Этап обработки выдачи / отзыва |

Алгоритм обработки:

```text
для каждой новой записи из Souhu:
  если used_tx_id пустой: пропустить до следующей синхронизации
  если used_tx_id уже обработан: ничего не делать
  иначе:
    1. создать неизменяемую запись расхода;
    2. определить клиентскую цену 65K или 131K;
    3. списать клиентский баланс в одной транзакции БД;
    4. сохранить amount как закупочную цену;
    5. сохранить маржу = розничное списание - закупочная цена;
    6. обновить progress по текущему 72-часовому циклу;
    7. проверить лимит баланса и при необходимости остановить сервис.
```

На `used_tx_id` нужен уникальный индекс. Если Souhu возвращает событие без `used_tx_id`, использовать временный fingerprint из адреса, `delegate_tx_id`, `createtime` и суммы, а повторную обработку такого события не выполнять автоматически до проверки.

## 8. Пауза, возобновление и повторное пополнение

Пауза:

```text
POST /update_energy_smart
address=T...
status=stop
```

Возобновление:

```text
POST /update_energy_smart
address=T...
status=start
```

Повторное пополнение — снова `POST /delegate_energy_smart` с `address` и положительным `balance`.

Перед любым повтором запроса, оборванного по timeout, не отправлять его слепо повторно: в API не описан idempotency key. Сначала запросить текущее состояние адреса и зафиксировать случай для ручной сверки, иначе есть риск дважды пополнить кредит Souhu.

## 9. Что показывать клиенту

Экран автозаряда:

```text
Автозаряд Pro
Статус: подключён / пауза / требуется пополнение
Розничный баланс: 18.40 TRX
Залог: 15 TRX (удержан поставщиком)
Текущая цена: 65K — X TRX, 131K — Y TRX
Расход в цикле: 318 200 / 460 000 энергии
```

История должна показывать:

- дату и время;
- 65K или 131K;
- израсходованную энергию;
- клиентскую цену;
- ссылку на `used_tx_id` в TronScan;
- статус обработки.

Нужны явные предупреждения:

- Pro / Max / Ultra невыгодны для редких переводов;
- условие измеряется расходом энергии за 72 часа;
- залог зависит от правил Souhu;
- при недостатке рабочего баланса автозаряд ставится на паузу.

## 11. Смена тарифа

Не переключать канал задним числом простым редактированием записи БД. Souhu в публичном канале упоминает «запланированное переключение» после окончания текущего периода, однако способ вызова через API не описан.

До получения отдельной документации реализовать так:

1. Клиент выбирает новый тариф.
2. Сохраняем `pending_tariff`.
3. Не вызываем Souhu на переключение автоматически.
4. После подтверждённого окончания периода либо выполняем согласованный с Souhu API-вызов, либо просим оператора выполнить смену вручную.

## 12. Обязательные тесты до запуска для реальных клиентов

Swagger не описывает полный жизненный цикл залога. До публичного запуска сделать на собственном тестовом адресе:

1. **Pro без расхода**: подключить с `hf_deposit=15`, дождаться 72 часов, сохранить все ответы API до и после.
2. **Pro с расходом выше 460K**: выполнить операции, дождаться завершения 72 часов, проверить возврат залога.
3. **Следующий период после успешного Pro**: проверить, начинается ли новый цикл сам, удерживается ли залог снова и как это отражается в API.
4. Повторить для Max и Ultra.
5. Проверить поведение при `status=stop` внутри периода.
6. Проверить поведение при исчерпании кредита Souhu.
7. Проверить `net_protect=open` и `net_protect=close` на тестовом адресе.
8. Проверить, какие данные реально возвращает `/get_smart_price` для `jisu_frequency` и `guangsu_frequency`.

До окончания тестов клиенту нельзя обещать автоматический возврат залога в конкретный момент или на конкретный баланс.

## 13. Вопросы Souhu, на которые нужен письменный ответ

```text
1. Куда зачисляется возвращённый залог: на баланс адреса в Smart Delegation или на основной баланс API-аккаунта?
2. Что происходит с залогом, если минимум не выполнен: он сгорает полностью, частично или переносится?
3. Начинается ли следующий 72-часовой период автоматически? Удерживается ли новый залог автоматически?
4. Что происходит с активным периодом при stop / start?
5. Нужно ли передавать hf_deposit при повторных пополнениях balance?
6. Каким API-методом безопасно переключать high_frequency → jisu_frequency → guangsu_frequency?
7. Какие точные поля и цены возвращает get_smart_price для Max и Ultra?
8. Что делают net_protect=open и net_protect=close?
9. Есть ли webhook, API для статуса цикла, залога и его возврата?
10. Какой максимальный polling rate допустим для query_energy_smart?
```

## 14. Критерии готовности MVP

- [ ] Подключение `normal`, `pro`, `max`, `ultra` через точные `channel`.
- [ ] Корректная HMAC-подпись и обработка времени.
- [ ] Розничный баланс клиента отделён от кредита Souhu.
- [ ] Отдельно учитывается залог.
- [ ] Уникальная и идемпотентная обработка `used_tx_id`.
- [ ] CRON синхронизации с логами и алертами ошибок.
- [ ] Пауза при недостатке клиентского баланса.
- [ ] Экран статуса и истории для клиента.
- [ ] Админский просмотр: закупка, розничное списание, маржа, расхождение балансов.
- [ ] Завершены тесты 72-часового цикла и зафиксированы реальные правила Souhu.
